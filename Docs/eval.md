# Evaluation Plan: Mutual Fund FAQ Assistant

How each phase in [implementation_plan.md](implementation_plan.md) is evaluated: what is measured, the test data, how it is graded, and the pass thresholds. Requirements come from [problemStatement.md](problemStatement.md), design from [architecture.md](architecture.md), and case IDs (e.g. `PII-13`) from [edge_case.md](edge_case.md).

## 1. Principles

1. **Deterministic grading first.** Most checks are exact: string/regex matches, URL equality, counts, HTTP status codes, database inspection. No LLM-as-judge is used for pass/fail.
2. **Wrong is worse than missing.** A "not found" reply is a miss; a wrong figure is a failure. Targets reflect this: wrong-value rate must be 0.
3. **Compliance targets are 100%.** Advisory refusal, PII blocking, one link per response, and footer presence have no tolerance.
4. **Every phase re-runs the earlier phases' evals.** A phase is not done if it regresses an earlier one.
5. **LLM cases are run more than once.** Groq output at temperature 0 is not guaranteed identical across calls, so every case that touches a model is run 3 times and passes only if all 3 runs pass.

## 2. Eval Assets

All under `tests/`:

| File | Contents | Started in |
|---|---|---|
| `gold_facts.yaml` | One entry per scheme × fact: official value, source document, `as_of`, and the document's content hash at labelling time | Phase 1 |
| `eval_questions.yaml` | Single-turn questions with expected intent, scheme, template, and answer checks | Phase 1 (factual), grows in Phases 2–3 |
| `conversations.yaml` | Scripted multi-turn threads for follow-up, isolation, and concurrency tests | Phase 4 |
| `pii_cases.yaml` | Positive (must block) and negative (must allow) messages per PII type | Phase 3 |
| `fixtures/` | Sample HTML/PDF files, including broken and edge-case files for parser tests | Phase 1 |
| `run_eval.py` | Runner: `python -m tests.run_eval --phase N [--category C] [--runs 3]` | Phase 1 |
| `results/` | One JSON + Markdown report per run, named `<date>-phase<N>.{json,md}` | Phase 1 |

### 2.1 Question entry format

```yaml
- id: F-MIDCAP-EXPENSE-01
  category: factual            # factual | not_found | advisory | performance | nav | multi_scheme
                               # greeting | out_of_scope | clarification | mixed | adversarial
  question: "What is the expense ratio of HDFC Mid Cap Fund – Direct Growth?"
  expected:
    intent: factual
    scheme_id: hdfc-mid-cap
    needs_scheme: false
    advisory_aside: false
    template: null              # or the template name for non-factual categories
    gold_fact: hdfc-mid-cap.expense_ratio_direct   # key into gold_facts.yaml
    source_docs: [factsheet]    # acceptable cited source types (first is preferred)
  edge_cases: [RAG-01, PRS-05]
```

### 2.2 Gold fact format

```yaml
hdfc-mid-cap.expense_ratio_direct:
  value: "<copied exactly from the document, with unit>"
  accept: ["<equivalent forms, e.g. '0.77%' and '0.77 %'>"]
  source_url: "<registry URL>"
  as_of: "2026-09-30"
  doc_hash: "<content hash when labelled>"
```

Gold values are labelled **by a person reading the official document**, never generated by the system. The runner compares `doc_hash` with the current document hash and marks entries **stale** when the source changed, so they get re-labelled instead of failing silently.

## 3. Metrics

| Metric | Definition |
|---|---|
| **Fact recall (chunk level)** | Share of gold facts whose value appears in at least one chunk tagged with the correct `scheme_id` |
| **Retrieval recall@k** | Share of factual questions where a chunk from an acceptable source document containing the gold value is in the top k |
| **Factual accuracy** | Share of factual questions whose answer contains the gold value (or an `accept` form) |
| **Wrong-value rate** | Share of factual + not-found questions whose answer states a figure that is not the gold value |
| **Not-found honesty** | Share of not-found questions answered with the "not found" template |
| **Citation correctness** | Share of answers whose link is the gold `source_url`, or a registry URL of an acceptable `source_docs` type for the same scheme |
| **Footer correctness** | Share of responses whose footer date equals the cited document's stored `as_of` (else `fetched_at`) |
| **Format compliance** | Share of responses with ≤ 3 sentences, exactly 1 link, footer present |
| **Intent accuracy** | Classifier intent matches expected; reported as a confusion matrix |
| **Advisory leak rate** | Share of advisory/adversarial questions that got anything other than a refusal template |
| **False refusal rate** | Share of factual questions that got a refusal or out-of-scope template |
| **PII recall / false-positive rate** | Share of positive PII cases blocked / negative cases wrongly blocked |
| **Stability** | Share of LLM cases that pass all 3 runs |
| **Latency** | p50 / p95 time from API request to response, factual questions only |

### Phase 6: Full Evaluation and Tuning

1. Run every automated check from Phases 0–4 with `--runs 3`.
2. Run the Phase 5 checklist once more.
3. **Human review:** a person reads 30 randomly sampled responses (at least 10 factual, 10 refusals/templates, 5 conversation turns) and scores each on the rubric below.
4. Triage each failure into one bucket and fix in the owning phase: **parsing** (1), **retrieval** (2), **classifier prompt** (3), **generator prompt** (2), **validator rule** (3), **API/threads** (4), **UI** (5), **gold label wrong** (re-label).
5. Re-run until the scorecard passes.

**Human review rubric** (each response scored pass/fail on every row):

| Criterion | Pass when |
|---|---|
| Correct | Matches the cited official document |
| Facts-only | No opinion, recommendation, or prediction |
| Clear | A retail investor would understand it without extra context |
| Polite | Refusals are courteous and say what the bot *can* help with |
| Useful link | The link is the most relevant official page for the question |

Pass: ≥ 28 / 30 on every criterion, and 30 / 30 on Facts-only.

## 5. Running and Reporting

- **Pacing:** the runner limits requests per minute (`--rpm`, default below the Groq account limit) so evals don't trip Groq rate limits (LLM-08). A Groq 429 during an eval is retried by the runner, not counted as a failure.
- **Scope flags:** `--phase N` runs that phase's checks plus all earlier phases; `--category` and `--ids` re-run a subset while fixing failures.
- **Report contents:** git commit, config (models, `MIN_SIMILARITY`, `RETRIEVAL_TOP_K`), corpus snapshot (document count and latest `fetched_at`), every metric with its threshold and pass/fail, a confusion matrix for the classifier, flaky cases (passed some runs, not all), stale gold entries, and the full list of failures with question, expected, actual, and cited URL.
- **When to run:**
  - after each phase (that phase and all earlier ones)
  - after any prompt, model, or threshold change (Phases 2–3 at minimum)
  - after each re-ingestion that reports updated documents (re-label stale gold entries first)
